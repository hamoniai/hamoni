= Database design and principles
:navtitle: Database design and principles

This page describes the database design and the rules that govern it. The
detailed requirements are recorded in
link:{project-base-url}/blob/main/API-AND-DATABASE.md[API and database contract].

== Two tiers of schema

There are two kinds of schema:

* **The global schema.** Application-managed and self-cleaning. It holds the
  authentication profiles — the link from an inbound OIDC context to a Hamoni
  identity and the organisation pointers that identity may enter. No user
  transacts in the global schema.
* **The organisation schema.** One per organisation. It holds everything
  organisation-scoped: user profiles, team and project configuration, process
  and deployment state, and the organisation's audit trail.

Global tables are addressed with an explicit schema qualifier. Every other table
belongs to the organisation schema named by the organisation identifier.

== Isolation by schema

Isolation is by schema, not by a discriminator column. The schema is part of the
query's identity, so there is no filter for a developer to forget and no way for
a query against one organisation to reach another.

A missing or wrong tenant selection is a defect. There is no cross-schema
foreign key.

== Single-organisation mode

A deployment-level flag selects multi-organisation or single-organisation mode.
The default is single-organisation: the deployment supports exactly one
organisation and creating new organisations is disabled.

Single-organisation and multi-organisation deployments use the same dependency
set. Multi-organisation adds organisation schemas, not additional platform
services.

== Migrations

Schema changes are forward-only and applied with Flyway. An applied migration is
never edited. Migrations are split into global and per-organisation sets and
applied to every organisation schema. Creating an organisation creates and
migrates its schema.

A rolling deployment may run two application versions against one schema, so the
working direction is that upgrades make safe, additive changes (ADR-0058,
proposed). A breaking change must be made in steps that keep both versions
viable.

== Identity attributes

Name and email are owned by the OIDC claims and are never edited in Hamoni. They
are stored as a cached projection and refreshed on the next sign-in or token
validation. A person who changes their name or email does so at the provider.

== Conventions

* **Identifiers** are `java.util.UUID`, generated at the boundary. The database
  stores the native UUID type; the interface presents a string.
* **Foreign keys** express structural relationships within a schema. The column
  is `<table>_id` and the property is `<table>Id`.
* **Naming** is `snake_case` for tables and columns; Kotlin and TypeScript use
  the matching `camelCase`.
* **Timestamps** are `java.time.Instant` in Coordinated Universal Time.
* **Money and decimals** are `BigDecimal` with precision 15 and scale 5, never a
  binary floating-point type. Money carries an explicit currency.
* **Enumerated states** are stored as constrained strings and mapped to the
  sealed domain type.
* **Optimistic locking** guards aggregates that can be edited concurrently; a
  conflict surfaces as a domain outcome, not a server error.
* **Transactions** are explicit and short. No remote call sits inside one.
* **Audit** writes go through the Hamoni audit framework into the organisation's
  audit store; they are not best-effort.

== Documents

A document is a reference to a file blob, not a row containing the file.
Business data holds the document identifier. A template is the content a
document is generated from and is reused across processes. Document access
derives from the process instance's access rules.

The concrete storage, streaming and permission rules remain open.
