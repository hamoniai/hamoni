= Project layout
:navtitle: Project layout

This page describes how the Hamoni repository and its build projects are
organised. It is about the software layout, not the runtime solution
architecture.

== Repository structure

[#component-structure]
.Component structure
[svgbob]
----
+----------------+                  +------------------+
|  control room  |                  |  process runner  |
| design and API |                  |    execution     |
+--------+-------+                  +--------+---------+
         |                                   |
         |                                   |
         +---------------+-------------------+
                         |
                         v
                 +-------------------+
                 |      common       |
                 | model and schema  |
                 | state and API     |
                 +-------------------+
----

The repository has three holding directories plus the documentation set:

* `control-room/` — the user-facing application: the process designer,
  management, lists, teams, projects and security.
* `process-runner/` — the execution runtime: the process engine, state machines,
  pend and exception, signals, timers and the audit trail.
* `common/` — the models, contracts and utilities genuinely shared by both
  application areas.
* `docs/` — the Antora documentation component.

Dependencies are one-way. A project under `control-room/` or `process-runner/`
may depend on a project under `common/`. The two application areas never depend
on each other, and `common/` depends on neither.

== Current projects

The projects today are:

[cols="2,3",options="header"]
|===
| Project | Purpose

| `control-room/control-room`
| The Quarkus assembly for the Control Room. It serves the Angular application
through Quinoa and exposes the interface the screens use.

| `control-room/control-room-ui`
| The Angular front end. It owns presentation, localisation resources and the
client services that call the Control Room.

| `process-runner/process-runner`
| The Quarkus assembly for the Process Runner. It executes process definitions
and has no REST interface.

| `common/common-core`
| Core concepts and shared libraries used across the application areas.

| `common/common-platform`
| Common Quarkus platform functionality and configuration.

| `common/common-test`
| Test support shared by the other projects.

| `docs`
| The Antora documentation component.
|===

== Project names and packages

A project is named `<area>-<name>` and maps to the package
`ai.hamoni.<area>.<name>`. An assembly project named after its area maps to the
area root. For example:

* `common-platform` maps to `ai.hamoni.common.platform`;
* `control-room-<name>` maps to `ai.hamoni.control_room.<name>`;
* the `control-room` assembly maps to `ai.hamoni.control_room`.

The package structure follows the standard packages described in the
link:{project-base-url}/blob/main/CODING-STANDARDS.md[Coding standards], §2:

* `data` — JPA entities, data objects and projections;
* `processor` — Quarkus Reactive Messaging endpoints;
* `service` — service beans;
* `resource` — REST API endpoints and shared request/response plumbing.

A project root may also hold configuration and constants. Add another package
only when it has a clear purpose of its own.

== Build and conventions

The build is driven by Gradle with the Kotlin DSL. Common configuration comes
from the shared Hamoni Gradle convention plugins; project build files declare
only their own dependencies. Every library and version is declared once in
`gradle/libs.versions.toml`.

The Gradle wrapper is committed. Use `./gradlew`, never a system `gradle`.

== Tests and boundaries

Tests mirror the package of the class under test and are named after it. A test
class lives in the same package as the class under test, and a source file with
several classes is tested by one test file named after the source file.

ArchUnit guards the architectural boundaries: no dependency from one application
area to the other, and `common/` depends on neither. The testing rules are in the
link:{project-base-url}/blob/main/CODING-STANDARDS.md[Coding standards], §16.
